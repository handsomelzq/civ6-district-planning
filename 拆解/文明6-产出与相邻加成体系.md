## 2. 产出体系概览

### 2.1 产出类型全集

`Yields.xml` 里**只有六种**：

| id | 名称 |
|---|---|
| `YIELD_FOOD` | 粮食 |
| `YIELD_PRODUCTION` | 生产力 |
| `YIELD_GOLD` | 金币 |
| `YIELD_SCIENCE` | 科技 |
| `YIELD_CULTURE` | 文化 |
| `YIELD_FAITH` | 信仰 |

大人物点数、宜居度、住房、忠诚度等**不在 `Yields` 表里**，它们是各自独立的系统（`District_GreatPersonPoints`、`AppealHousingChanges` 等）。相邻加成只作用于这六种产出——这是个很干净的边界，也是本项目能把范围收在「产出求值」上的原因。

### 2.2 产出的来源分类，以及一个反直觉的事实 ⭐

一座城市的产出可分解为：

| 来源 | 数据位置 | 本项目是否建模 |
|---|---|---|
| 地块基础产出 | `Terrains` / `Features` / `Resources` / 自然奇观 | ✅ |
| **区域基础产出** | —— **不存在**，见下 | —— |
| **相邻加成** | `Adjacency_YieldChanges` + `District_Adjacencies` | ✅ 本篇深拆对象 |
| 建筑产出 | `Building_YieldChanges` | ✅ |
| 每市民产出 | `District_CitizenYieldChanges`（14 行） | ⚠️ 需要人口分配，本期不做 |
| 文明 / 领袖修正 | `Traits` 及其 `Modifiers` | 部分 |
| 政策卡 / 宗教 / 奇观 / 总督 | 各自的 `Modifiers` 体系 | ❌ 不做 |

⭐ **反直觉的事实：文明 6 的区域本身不产出任何东西。**

`districts.csv` 全部 36 行的 `基础产出` 都是「无」——游戏数据里根本没有「区域基础产出」这张表。一座学院的科技产出，完全来自三处：**相邻加成、其上的建筑、以及在其上工作的市民**。

这个事实改变了整套系统的定性：

> **相邻加成不是「锦上添花的加成」，它就是区域产出的本体。**

很多玩家（包括写这份拆解之前的我）会下意识以为区域有个基础产出、相邻加成在它之上叠加。实际上没有基座——把学院放在一块没有山、没有雨林、没有邻居的平地上，它的科技产出是 **0**（在建图书馆、派市民之前）。

这解释了两件事：

1. **为什么文明 6 的城市规划压力这么大。** 放错位置不是"少赚一点"，而是这个区域**什么都不产**。惩罚是绝对的而不是边际的。
2. **为什么本项目可以只做静态求值就有意义。** 如果区域产出以基座为主、相邻为辅，那么"摆得好不好"只影响一个小尾数，做成游戏不成立。正因为相邻加成承担了全部，一个纯粹的"摆位置"游戏才有足够的决策空间。

> 顺带一个术语澄清：`District_CitizenYieldChanges` 是「每个在此区域工作的市民产出多少」（例如学院每市民 +2 科技），**不是**区域自身产出。这两者容易混淆，而它们在建模上完全不同——后者需要人口分配系统，是本项目明确砍掉的部分（见 [../设计/立项书.md](../设计/立项书.md) §四）。

## 3. 相邻加成的数据模型（本篇核心）

### 3.1 规则存在哪里

相邻规则由**两张表 + 一张排除表**构成：

| 表 | 字段 | 作用 |
|---|---|---|
| `Adjacency_YieldChanges` | 见 §3.2 | 定义规则本身（给什么产出、多少、条件是什么） |
| `District_Adjacencies` | `DistrictType`, `YieldChangeId` | **把规则挂到区域上**，多对多 |
| `ExcludedAdjacencies` | `YieldChangeId`, `TraitType` | 按文明 trait **排除**某条规则 |

⭐ **规则与区域是多对多，这是整个设计里最关键的一处解耦。** 一条规则可以挂在多个区域上（`Government_Science` 挂在 15 个区域上），一个区域也挂多条规则。所以「给所有区域加一条相邻政府广场的加成」这种改动，只要在 `District_Adjacencies` 里加 15 行挂接，**不需要碰任何一条规则定义**。

这个解耦的代价是：想知道"学院有哪些相邻加成"必须做一次 join，不能只看一张表。本项目的 `adjacency_rules.csv` 是**去规范化**的（一区域一行，103 行），把 join 预先做掉了——代价是同一条规则会重复出现，所以 `规则id` 必须用复合形式（见 §8）。

### 3.2 字段逐一解读

| 字段 | 取值 | 玩法含义 |
|---|---|---|
| `ID` | 字符串 | 规则标识。**不是**本项目的主键，见 §8 |
| `Description` | LOC 键 | 玩家在提示里看到的说明文本 |
| `YieldType` | 六种产出之一 | 加什么 |
| `YieldChange` | 数值，**可为负** | 加多少。全库唯一的负值是韩国书院的 −1 |
| `TilesRequired` | `1` 或 `2`；缺省取表结构默认值 `1` | **档位**：1 = 主要相邻，2 = 标准相邻。见 §4 |
| `AdjacentTerrain` | 地形 id | 相邻某种地形 |
| `AdjacentFeature` | 地貌 id | 相邻某种地貌 |
| `AdjacentDistrict` | 区域 id | 相邻某种区域。**按 id 精确匹配，不匹配其替换区域**，见 §5.1 |
| `AdjacentImprovement` | 改良设施 id | 相邻某种改良设施 |
| `AdjacentResourceClass` | `BONUS`/`LUXURY`/`STRATEGIC`/`LEY_LINE` | 相邻某**类**资源 |
| `AdjacentResource` | `true` | 相邻任意资源 |
| `AdjacentSeaResource` | `true` | 相邻任意海洋资源 |
| `AdjacentRiver` | `true` | 临河 |
| `AdjacentWonder` | `true` | 相邻世界奇观 |
| `AdjacentNaturalWonder` | `true` | 相邻自然奇观 |
| `OtherDistrictAdjacent` | `true` | 相邻**任意其他区域** |
| `Self` | `true` | 见 §5.1 第 3 条，语义待实测 |
| `PrereqTech` / `PrereqCivic` | 科技 / 市政 id | 规则生效的前置 |
| `ObsoleteTech` / `ObsoleteCivic` | 科技 / 市政 id | 规则失效的条件 |

两处值得注意：

- **目标字段分成两类取值形态**：`AdjacentTerrain` / `AdjacentFeature` / `AdjacentDistrict` / `AdjacentImprovement` / `AdjacentResourceClass` 填**具体标识**；其余全部只填 `true`，是布尔开关。本项目的 `目标类别` + `目标id` 两列就是按这个分界设计的（布尔类的 `目标id` 一律为 `无`）。
- **`TilesRequired` 缺省合法**。书院的 `BaseDistrict_Science` 就没写这一列，取表结构里的 `DEFAULT 1`。解析时必须去游戏自带的 `Base/Assets/Gameplay/Data/Schema/01_GameplaySchema.sql` 取默认值，不能当空值处理，也不能自己猜一个。

### 3.3 这个结构的形态判断

**已核实**：文明 6 用的是**宽稀疏表**——相邻目标的类型由一组互斥的可空列表达，每行只填其中一列，其余全空。12 个目标列里，全库最多的 `AdjacentDistrict` 也只在部分行有值。

代价：新增一种可被相邻的目标类型就要加一列，且每行都要为不用的列留空。
好处：查询时不需要多态分发，SQL 可以直接按列过滤——而文明 6 的玩法数据本来就是灌进 SQLite 的，这个选择与它的存储实现是一致的。

本项目改用 `目标类别 + 目标id` 两列的多态写法，理由与取舍见 §8。

## 4. 分档语义：主要相邻与标准相邻

**初稿待复核**：规则用「所需数量」字段区分两档——

| 档位 | 所需数量 | 语义 |
|---|---|---|
| 主要相邻 | 1 | 每个符合条件的相邻目标给满额加成 |
| 标准相邻 | 2 | 每 2 个符合条件的相邻目标给满额加成 |

### 4.1 这个设计的精妙处

**初稿待复核**：用**一个整数字段**表达了"强关联"与"弱关联"的区别，而没有引入第二套机制。山脉对学院是强关联（每座都给满），另一个区域对学院是弱关联（要两个才给满）——这个语义差别完全由 `1` 和 `2` 承载。

对比一下如果用两张表、或者用一个"加成类型"枚举来表达，复杂度都会上升而表达力不变。**这是数据模型设计上一处值得学习的克制。**

### 4.2 非整除情形与取整 ⭐

标准档下 3 个相邻目标给多少？取整发生在哪一层（逐规则 / 逐区域 / 汇总后）？

❓ **必须以数据 + 游戏内实测双重确认，不得凭印象填写。** 这是全篇优先级最高的未决项——它影响每一条标准档规则的每一次求值，错一次会污染全部结论。

实测方法：在游戏内构造已知局面（如学院旁恰好 1 / 2 / 3 个相邻区域且无其他加成源），逐一读取产出面板数值。

另有 **85 条规则挂在改良设施上**（`Improvement_Adjacencies`，即"改良设施吃邻居"，例如梯田吃山脉、圩田吃圩田）。那是一套与区域相邻**并行且独立**的体系，本项目本期不做（见 [../设计/SDD-局面求值器.md](../设计/SDD-局面求值器.md) §10 D7）。**拆解时不要把两套混为一谈**——它们共用 `Adjacency_YieldChanges` 这张规则表，但挂接表不同。

### 5.1 四个需要单独查清的匹配行为

**1. 同一个邻格被多条规则各计一次？——结构上是，且这是高频情形。**

最清楚的例子：商业中心旁边有一个港口。这一格同时被两条规则命中：

- `Harbor_Gold`（相邻港口，+2/1 格）
- `District_Gold`（任意其他区域，+1/2 格）

数据里**没有任何"已被具体规则命中就不再计入通用规则"的排除机制**——`ExcludedAdjacencies` 是按文明 trait 排除整条规则，不是按命中去重。所以结论是各计一次。

这不是边角情况，而是文明 6 布局的核心算术：一个具体加成很高的邻居**同时**还在为通用区域加成计数。

**2. 一格既是山脉又临河？——同理，两条规则各自独立计数。**

不同规则有各自独立的计数器，互不知晓。

> ⚠️ 上面两条是**从数据结构推出的**结论（没有去重机制 ⇒ 不去重），不是实测结论。引擎层是否另有去重逻辑，需要游戏内验证——见 [../设计/测试清单.md](../设计/测试清单.md) §2。

**3. `Self` 的语义 —— 待实测。**

全库唯一一条 `Self="true"` 是韩国书院的 `BaseDistrict_Science`（+4 科技），只挂在书院上。但**区域不可能与自己相邻**，所以这条在效果上像"无条件固定值"而非字面的"相邻同类"。这决定求值器把 `自身` 当常数项还是相邻项，必须实测（见测试清单 §2.2）。

**4. 特色区域是否被「相邻 X 区域」匹配？——不匹配。** ⭐

答案由数据自己的设计给出：`Harbor_Gold`（相邻港口 +2 金币）与 `RoyalDock_Gold`（相邻皇家海军船坞 +2 金币）作为**两条独立规则并存**，而皇家海军船坞正是港口的替换区域。**若 `AdjacentDistrict` 会自动匹配替换关系，`RoyalDock_Gold` 这一行就是冗余的**——它的存在本身就是答案。

所以"汉萨算不算工业区"的答案是**不算**。这条对实现是好消息：不需要任何「替换等价」逻辑，按 id 精确匹配即可。对设计则是个负担——Firaxis 每加一个特色区域，就要为它把所有相关规则重写一遍（`Cothon_Gold`、`Lavra_Gold`、`Suguba` 系列都是这么来的）。详见 [文明6-文明与领袖特色.md](文明6-文明与领袖特色.md)。

## 6. 前置与废弃机制：一个分布上的意外 ⭐

`Adjacency_YieldChanges` 有 `PrereqTech` / `PrereqCivic` / `ObsoleteTech` / `ObsoleteCivic` 四个条件字段，全库分别用在 19 / 12 / 9 / 8 行上。

**但它们的分布极不均匀，而且分布本身就是结论：**

| 挂接侧 | 带条件的规则数 |
|---|---|
| 区域侧（`District_Adjacencies`，103 条） | **0** |
| 改良设施侧（`Improvement_Adjacencies`，85 条） | 全部 19 / 12 / 9 / 8 条都在这里 |

也就是说：**区域的相邻加成完全不随科技变化。** 学院旁边那座山，从远古时代到信息时代都是 +1 科技，一次都不会变。所有随科技演进的相邻加成——农场随封建主义与可互换部件两次升级、圩田、梯田、巨石头像、长城——**全部属于改良设施**。

### 6.1 这个分布说明了什么

**初稿待复核。** 这不是随机的实现细节，它对应一条清晰的设计分工：

| | 区域相邻 | 改良设施相邻 |
|---|---|---|
| 随科技演进 | 否 | 是 |
| 决策的可逆性 | **不可逆**（区域拆不掉） | 可逆（改良设施可以重建、覆盖） |
| 玩家做决策时的信息 | 完整且永久有效 | 会过时，需要预判 |

**区域是不可逆决策，所以它的规则必须稳定**；改良设施是可逆决策，所以它的规则可以随时代变动而不伤害玩家。这是一个非常讲究的设计选择：把"需要长期规划的东西"和"会变的东西"分到了两套体系里，**让不可逆的决策永远不会因为规则变化而事后变蠢**。

> 这一条推翻了我写骨架时的猜测。我原本写的是「前置科技机制让现在不划算的布局在后期变划算，创造了长期规划空间，但界面没提示，是设计意图与信息呈现的脱节」。实际情况正好相反：**文明 6 有意不让区域相邻随科技变化**，所以既不存在那个长期规划空间，也就不存在那个脱节。
>
> 教训：光看到字段存在（`PrereqTech` 确实在表里）就推论玩法，会推错。**必须看那些字段实际落在哪些行上。**

### 6.2 对本项目的直接影响

- 求值器的产出计算**不需要科技集合**：给定布局，产出唯一
- 但区域与建筑的**可建性**依赖科技（`districts` 36 行中 23 行带前置科技，`buildings` 85 行中 41 行带前置科技），所以局面仍要声明科技状态，只是它进入合法性校验而非产出计算
- 详见 [../设计/SDD-局面求值器.md](../设计/SDD-局面求值器.md) §3.2（该节已按此更正）
- ⚠️ **一旦把改良设施相邻纳入范围，这一切都反转**：19 条带前置的规则全部进场，产出届时确实会依赖科技状态

## 7. 规则分布

**全量清单以 `../配置表/adjacency_rules.csv` 为准**（103 行，每行带 `原始标识` 可回溯到游戏数据）。本节只写分布与从分布里读出来的东西。

### 7.1 有相邻加成的区域只有 16 个

| 区域 | 规则数 | 产出 | 备注 |
|---|---|---|---|
| 学院 | 12 | 科技 | 山脉 ×5、雨林、任意区域、政府广场、地热裂缝、礁石、大堡礁、棉花堡 |
| 圣地 | 10 | 信仰 | 山脉 ×5、森林、任意区域、政府广场、自然奇观、棉花堡 |
| 工业区 | 10 | 生产力 | 水渠/浴场/运河/堤坝各 +2、矿场与伐木场各每 2 个 +1、采石场 +1、战略资源 +1 |
| **拉夫拉**（俄罗斯） | 10 | 信仰 | **与圣地完全相同的 10 条** |
| 剧院广场 | 9 | 文化 | 世界奇观 +2、四类娱乐区各 +2、任意区域每 2 个 +1 |
| **卫城**（希腊） | 7 | 文化 | 见 §7.3 |
| 商业中心 | 7 | 金币 | 临河 +2、港口 +2、皇家海军船坞 +2、科索恩 +2 |

| **天文台**（玛雅） | 6 | 科技 | **吃改良设施而非山脉**：农场每 2 个 +1、种植园 +2 |
| **苏古巴**（马里） | 6 | 金币 | 吃圣地与拉夫拉各 +2 |
| 港口 / **科索恩**（腓尼基） / **皇家海军船坞**（英国） | 各 4 | 金币 | 三者规则结构相同 |
| **奥皮杜姆**（高卢） | 3 | 生产力 | 采石场 +2、战略资源 +2（都是工业区的两倍） |
| **书院**（韩国） | 3 | 科技 | +4 固定、政府广场 +1、**任意区域 −1** |
| **城池**（越南） | 1 | 文化 | 任意其他区域 **每 1 个 +2** |

其余 20 个区域（城市中心、水渠、运河、堤坝、机场、太空港、娱乐区、邻里、军营等）**一条相邻规则都没有**——它们要么是基础设施，要么产出走别的机制。

### 7.2 政府广场是唯一的"万能邻居"

`Government_*` 五条规则（科技/文化/金币/信仰/生产力各一条，各 +1/1 格）通过 `District_Adjacencies` 挂在 **15 个区域**上。这是全游戏唯一一个"挨着谁都好"的区域。

它是《迭起兴衰》加进来的，而且是**主要档**（每 1 个 +1）而不是标准档。所以政府广场的选址实际上是整座城市布局的锚点——这一点在游戏里几乎没有被提示。

### 7.3 卫城不是"更强的剧院广场"⭐

这是全表最有意思的一组对比，也是关卡母题 E 的数据基础：

| | 剧院广场 | 卫城（希腊） |
|---|---|---|
| 任意其他区域 | `District_Culture` 每 **2** 个 +1 | `District_Culture_Standard` 每 **1** 个 +1 |
| 相邻城市中心 | 无 | **额外 +1** |
| 世界奇观 | +2 | +2 |
| 娱乐区 / 水上乐园 | 各 +2 | 各 +2 |
| 街头嘉年华 / 铜锣湾 / 竞技场 | 各 +2 | **全部没有** |
| 合计规则数 | 9 | 7 |

卫城把通用区域相邻从标准档升到主要档（等于翻倍），代价是**丢掉了三条针对特定娱乐区的 +2**。

所以它不是单调变强，而是**换了一种布局取向**：剧院广场想挨着特定的娱乐建筑群，卫城想挨着尽可能多的任意区域。两者的最优解形状不同——这正是母题 E「档位升级」需要的结构，而且比"数值更高"有意思得多。

### 7.4 越南城池是档位与数值的双重升级

`District_Culture_Major`：任意其他区域**每 1 个 +2 文化**。对比剧院广场的每 2 个 +1，单位邻居的收益是 **4 倍**。

而且它只有这一条规则——没有奇观加成、没有娱乐区加成。这是个极端设计：**把全部收益压在"挤在区域堆里"这一件事上**。如果要做一个"集群中心"母题（关卡设计 §2 母题 B）的极端示例关卡，城池是最干净的选择。

## 8. 与本项目实现的对应关系

本项目的 `adjacency_rules.csv` 与游戏原表的差异及理由：

| 维度 | 文明 6 原表 | 本项目 | 理由 |
|---|---|---|---|
| 目标类型的表达 | 一组互斥可空列（宽稀疏表） | `目标类别` + `目标id` 两列多态 | 新增目标类型不动表结构 |
| 规则标识 | `ID` 列，**在去规范化后不唯一** | 复合形式 `区域id@原始标识` | 要在玩家可见的拆解面板中显示，并作为对账锚点。103 行里只有 64 个唯一原始标识，裸用会冲突 39 次 |
| 规则与区域的关系 | 多对多（靠 `District_Adjacencies` 挂接） | 去规范化为一区域一行 | 查询方便，代价是规则定义重复出现 |
| 条件字段 | 四个（前置/废弃 × 科技/市政） | 原样保留 | 区域侧当前全为空，但保留字段以备纳入改良设施 |
| id 体系 | 原始标识 | **保留原始标识** | 可对账优先于可读性 |

> 这张表是面试时最值得主动讲的一页：它说明拆解不止停在"规则是什么"，而是到了"规则为什么这样存、能不能存得更好"。

## 9. 设计评价

> **初稿待复核。** 以下是判断，不是复述——这一节是本篇的重点。

### 9.1 这套设计好在哪

> 下面前三条是从一手数据里读出来的，光靠玩游戏很难注意到。

1. **没有基础产出，所以相邻加成承担全部。**（见 §2.2）区域自身零产出，这使"摆位置"的惩罚是**绝对**的而不是边际的——放错地方不是少赚一点，而是这个区域什么都不产。很多同类游戏的建筑有个保底产出、位置加成只是小尾数，那样的系统里空间决策是可以糊过去的；文明 6 不行。这一条是整个区域规划玩法的承重墙。

2. **不可逆的决策配稳定的规则，可逆的决策配演进的规则。**（见 §6.1）区域相邻加成**一条都不随科技变化**，而所有随时代升级的相邻加成全在改良设施侧。区域拆不掉，改良设施可以覆盖重建——所以文明 6 有意让不可逆决策的规则永久稳定，**让玩家早期的规划永远不会因为规则变化而事后变蠢**。这个分工在游戏里完全不可见，但它是"敢让玩家在开局第十回合做一个管一整局的决定"的前提。

3. **规则与区域多对多解耦。**（见 §3.1）规则定义与"谁吃这条规则"分在两张表里，所以给 15 个区域加一条政府广场相邻加成，只需加 15 行挂接，一条规则定义都不用改。这也让特色区域可以自由重组规则集——卫城与剧院广场共用大部分规则、只换其中两条，就产生了完全不同的布局取向（见 §7.3）。

4. **把地形阅读变成核心技能。** 相邻加成使"这块地长什么样"直接决定产出，玩家必须真的去看地图，而不是套模板。这为一个宏观的 4X 游戏提供了微观尺度的决策层，两个尺度形成互补而非竞争。

5. **完全数据驱动，因此可迭代、可模组化。** 规则以数据行存在，平衡调整不需要改代码，模组作者也能在没有源码的情况下改玩法。这与文明 6 未开放 gameplay 源码的事实互为因果——大量玩法语义被有意推进数据层。

6. **分档语义的克制。** 用一个整数字段（`TilesRequired`）表达强／弱关联（见 §4.1），没有为此引入第二套机制。

7. **一格只能放一个区域，制造了真实的稀缺。** 相邻加成的价值完全建立在这条约束上——没有它，所有加成都能同时吃满，决策消失。

### 9.2 代价与问题

1. **学习曲线极陡且不连续。** 相邻加成的规则量大、分散在各区域的说明文本里，新手在相当长的时间内根本不知道自己少拿了多少产出。游戏没有提供任何"规划视图"来帮助理解全局。

2. **负外部性只被用了一次，城市布局因此退化。** 文明 6 的相邻加成体系里，负值规则**全库只有一条**：韩国书院每相邻一个区域 −1 科技。除此之外区域挨在一起只有好处没有坏处，最优策略因此趋同于"尽量把所有区域挤成一团"。

   值得注意的是这一条负值规则的存在本身：它证明**引擎完全支持负向相邻，设计上也验证过可行**——书院正因为这条负值而拥有全游戏最独特的布局逻辑（要孤立放，与其他所有区域相反）。既然如此，这个机制没有被推广到普遍的用地相容性上，是一个**选择**，而不是能力限制。现实规划中最核心的矛盾——工业区必须存在但它伤害邻居——在文明 6 里只作为一个文明的负面特性出现了一次。

3. **前置科技的长期规划空间没有被界面兑现**（见 §6.1）。

4. **信息呈现依赖悬停，缺少全局视图。** 玩家能看到"这一格放学院给多少"，但看不到"我整座城的产出由哪些规则贡献"。要回答后者只能自己心算。

### 9.3 改进建议

> 每条建议都要写清"改什么、为什么、代价是什么"。

1. **把负向相邻从一个文明的特性推广为普遍的用地相容性。** 让工业类区域对居住类区域产生负加成，把"挤成一团"从最优解变成需要权衡的方案。
   **论证优势**：不需要论证"这个机制能不能成立"——书院已经证明了引擎支持、平衡可做、而且它产生的独特布局逻辑正是这个机制的价值所在。要论证的只是"为什么值得推广"。
   代价：数值平衡复杂度上升，且要防止某些区域变成纯负担永不被选（书院靠 +4 的高固定值补偿，这是个可借鉴的解法）。
   → **本项目将其列为第三模式**（见立项书 §三），与还原部分隔离，以免破坏严格对标的前提。

2. **在界面上显式标注未解锁的潜在相邻加成。** 把"此处解锁 X 科技后 +N"直接画在地块上，让 §6.1 的设计维度可见。代价：界面信息密度进一步上升。

3. **提供一个布局规划视图**：把整座城的产出摊开到规则级别，让玩家看见每一点产出的来源。
   → **本项目的自由模式与产出拆解面板正是这条建议的实现**（见 [../设计/SDD-自由模式.md](../设计/SDD-自由模式.md)）。

⭐ 第 3 条是本拆解与本 demo 的接缝：demo 不是"文明 6 的小型复刻"，而是**对拆解中发现的一处设计缺口的直接回应**。这个叙事把作品 #2 与 #5 焊成一件事。
