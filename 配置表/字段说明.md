## 零、通用约定

| 约定 | 规则 |
|---|---|
| 表头 | 中文 |
| 多值字段 | 用 `\|` 分隔，如 `科技:2\|金币:1` |
| 键值对 | 写作 `键:值` |
| 空值 | 写 `无`，不留空单元格 |
| 坐标 | 轴向坐标，写作 `q,r` |
| 布尔 | `是` / `否` |

### 数据来源标记（每张生成表必带两列）⚠️

游戏尚未安装期间，部分表先用二手资料填充。因此**所有生成表必须带这两列**：

| 字段 | 取值 | 说明 |
|---|---|---|
| 数据来源 | `一手` / `二手` | `一手` = 游戏本体数据；`二手` = 网络资料 |
| 待核 | `是` / `否` | 二手数据核对通过后改为 `否`，并把 `数据来源` 改为 `一手` |

规则：**`待核=是` 的行可以用于开发与验证架构，但不得出现在任何对外展示的产物中**（演示视频、作品集 PDF、README）。交付前跑一次检查，存在 `待核=是` 即阻断交付。

### id 命名：保留游戏原始标识 ⭐

与 `武侠RPGdemo` 的 `C001` / `S101` 编号法**不同**，本项目一律保留文明 6 数据中的原始 id（形如 `DISTRICT_CAMPUS`、`TERRAIN_MOUNTAIN`）。

理由：本项目的立身之本是**可对账**。保留原始 id 使任意一行配置都能直接回溯到游戏数据中的对应行；重新编号会在解析层引入一张映射表，而这张表是纯粹的错误来源，换不到任何好处。

| 类型 | 表 | 说明 |

| 手工表 | `levels.csv`、`level_tiles.csv` | 关卡是原创设计内容，人工维护（可由自由模式导出草稿） |

## 三、相邻规则（核心表）

### `adjacency_rules.csv`

**一行一条规则。** 这张表是本项目最重要的一张。

| 字段 | 类型 | 说明 |
|---|---|---|
| 规则id | id | **稳定唯一**，形如 `区域id@原始标识`（例：`DISTRICT_CAMPUS@Mountains_Science1`）。会出现在玩家可见的拆解面板中，也是对账锚点 |
| 区域id | id | 这条规则加成给哪个区域 |
| 目标类别 | 枚举 | 匹配什么类型的相邻物，见 §五 |
| 目标id | id 或 `无` | 具体目标；`无` 表示该类别下的任意目标（如「任意相邻区域」） |
| 产出类型 | 枚举 | |
| 加成值 | 数值 | 满足「所需数量」时给出的加成。**允许负值**——文明 6 中有一条（韩国书院每相邻一区域 −1 科技），见 [../设计/SDD-局面求值器.md](../设计/SDD-局面求值器.md) 边界 E4 |
| 所需数量 | 整数 | `1` = 主要档，`2` = 标准档。语义见 SDD §3.3 |
| 前置科技 / 前置市政 | id 或 `无` | 规则生效的前置 |
| 废弃科技 / 废弃市政 | id 或 `无` | 规则失效的条件 |
| 原始标识 | 文本 | 游戏数据中该行的原始标识，用于回溯 |
| 备注 | 文本 | |

**规则id 的生成**：`区域id` + `@` + 原始标识。

**为什么不能直接用游戏的原始标识做主键**：游戏里一条规则通过 `District_Adjacencies` 挂在多个区域上（例如 `District_Science` 挂在 15 个区域上），而本表是去规范化的「一区域一行」形式。实测 103 行里只有 64 个唯一原始标识，**直接用裸 id 会冲突 39 次**。复合形式既保证唯一，也保留了可对账性——裸 id 存在 `原始标识` 列。

同一份数据重复解析必须得到完全相同的 id 与行序（否则拆解面板里的 id 会在每次重新解析后变化，对账无从进行）。

### `excluded_adjacencies.csv` 相邻规则的排除表

**特色化的第三种手法**（除「替换区域」与「新增规则」之外）：按文明或领袖的 trait **排除**某条相邻规则。

| 字段 | 类型 | 说明 |
|---|---|---|
| traitid | id | 游戏里的 trait 标识 |
| 所属文明id | 多值 id 或 `无` | 该 trait 属于哪个文明 |
| 所属领袖id | 多值 id 或 `无` | 该 trait 属于哪个领袖 |
| 被排除规则标识 | 文本 | 指向 `adjacency_rules.原始标识`（**裸游戏 id，不是 `规则id`**） |
| 备注 / 数据来源 / 待核 | — | |

> **为什么要拆成「所属文明」与「所属领袖」两列**：游戏的 `ExcludedAdjacencies` 只有一个 `TraitType` 列，文明 trait 与领袖 trait **混在一起且没有区分字段**（12 行里 11 行属文明、1 行属波兰领袖雅德维加）。解析时显式查 `CivilizationTraits` / `LeaderTraits` 解出归属，否则求值器无法判断该排除在什么条件下生效。

这张表是**高卢**首期纳入的原因：高卢的核心特性就是被排除掉 5 条通用档区域相邻规则（`District_科技/信仰/金币/文化/生产力`），换来奥皮杜姆的采石场与战略资源加成翻倍。日本（`TRAIT_CIVILIZATION_ADJACENT_DISTRICTS`）也在这张表里，但它的「加法」部分走 Modifiers 体系，不在相邻规则表内。

## 三·二、战斗修正规则（与相邻规则同构的第二张核心表）

### `combat_modifiers.csv`

**一行一条修正。** 与 `adjacency_rules.csv` 刻意保持平行结构——两者都是「条件 → 修正值」，求值器用同一套累加机制处理（见 [../拆解/文明6-单位与军事叠力.md](../拆解/文明6-单位与军事叠力.md) §8）。

| 字段 | 类型 | 说明 |
|---|---|---|
| 修正id | id | **稳定唯一**，出现在战斗力拆解面板中，也是对账锚点 |
| 名称 | 文本 | 玩家可见，如「森林」「驻守」「大将军」 |
| 条件类别 | 枚举 | 见 §五 |
| 条件参数 | 多值键值或 `无` | 如 `地形:TERRAIN_HILLS`、`回合数:>=2`、`距离:2` |
| 修正通道 | 枚举 | 战斗力 / 远程战斗力 / 攻城战斗力 |
| 修正值 | 数值 | **可为负**（与相邻规则不同，战斗修正存在负值） |
| 作用时机 | 枚举 | 攻击时 / 防御时 / 始终 |
| 是否可叠加 | 布尔 | |
| 叠加上限 | 整数或 `无` | 如侧翼 6、支援 10（待一手核对） |
| 数据来源 / 待核 | — | 见 §零 |
| 备注 | 文本 | |

> **与 `adjacency_rules.csv` 的一处关键差异**：相邻规则的 `加成值` 恒为正（校验规则 5 会拦截负值），而战斗修正**允许负值**（沼泽 −2、受损惩罚、渡海登陆等）。两张表的校验规则因此不同，不可套用。

## 六·二、已知数据缺口（待补列）

解析已覆盖本项目当前需要的字段，但下面这些游戏里有、表里还没有的列，会在后续工作中变成障碍。**记录在此，补列时同步改解析脚本与 §七校验规则。**

| 表 | 缺的列 | 为什么需要 |
|---|---|---|
| `districts` | `OnePerCity`、`MaxPerPlayer` | **市政广场 `MaxPerPlayer=1`（全文明仅一座）是全系统权重最高的单个决策**，而现在这个约束只写在 `备注` 的自然语言里，求值器读不了 |
| `districts` | `NoAdjacentCity`、`Aqueduct` | 放置合法性判定要用（军营、伊坎达、保护区、城池不得紧邻城市中心） |
| `buildings` | 建筑替换标记（`BuildingReplaces`，15 行） | 特色建筑与基础建筑互斥，**直接按区域求和会重复计入** |
| `buildings` | 宗教建筑互斥标记（`EnabledByReligion`，9 栋） | 圣地的 9 栋宗教建筑是多选一，求和会把 +9 信仰算成 +33 |

后两条已经造成过实际错误：计算「建筑产出 vs 相邻加成量级」时若不剔除这两类互斥项，圣地的建筑链会被高算 3.7 倍。**做数值设计之前必须补上。**

## 七、跨表校验规则

`../Tools/check_config.py` 至少校验：

1. 所有外键存在：`adjacency_rules.区域id` → `districts`；`目标id` → 对应类别的表；`buildings.所属区域id` → `districts`；`districts.替换区域id` / `所属文明id` → 对应表
2. 所有枚举取值在 §五 范围内
3. `规则id` 唯一
4. `所需数量` ≥ 1
5. `加成值` 非零；**负值不算错误但要警告**（文明 6 中仅书院一条为负，新出现的负值大概率是配错，见 SDD 边界 E4）
6. 特色区域必有 `替换区域id` 与 `所属文明id`；非特色区域两者必为 `无`
7. `levels.csv` 引用的文明 / 领袖 / 地形 id 全部存在；`已解锁科技` / `已解锁市政` 的每一项都存在于 `techs` / `civics`
7b. 全项目范围的科技市政引用校验：`districts` / `buildings` / `units` / `adjacency_rules` 的 `前置科技` `前置市政` `废弃科技` `废弃市政` 全部可解析
8. `level_tiles.csv` 的每个 `关卡id` 在 `levels.csv` 中存在，且坐标无重复
9. 每关的 `贪心基线结果` 非空（见 SDD-挑战模式 边界 G10）
10. `combat_modifiers.规则唯一性`：`修正id` 唯一；`是否可叠加=否` 的行 `叠加上限` 必须为 `无`
11. `combat_modifiers.条件参数` 引用的地形 / 地貌 / 单位 id 全部存在
12. `units.时代` 非空（大将军的时代匹配依赖它）
13. **来源检查**：所有生成表必须含 `数据来源` 与 `待核` 两列；交付模式下存在任一 `待核=是` 即非零退出
14. **关卡非平凡性**：`关卡类别=普通` 的关卡，其 `贪心基线结果` 必须**没有达成**目标——单产出即严格小于 `目标值`，多产出即至少有一项分量没达标（见 [../设计/关卡设计.md](../设计/关卡设计.md) §5.2、§7.4）。`教学` 与 `对照` 两类豁免，各有自己的判据（同文档 §1.1 / §1.2）
15. `levels.母题` 取值在 A–F 范围内，**可以是 `+` 连接的组合**（L-07 = `B+C`，L-10 = `B+C+E`），逐段校验；标注依赖未决项的母题（D、F）任一段出现即不得进入已交付关卡
16. `excluded_adjacencies`：`所属文明id` 与 `所属领袖id` 不得同时为 `无`（排除规则必须有归属）；`被排除规则标识` 存在于 `adjacency_rules.原始标识`
17. `levels` 的星级阈值是**产出值**（2026-09-25 改）：必须满足 `目标值 ≤ 二星阈值 ≤ 三星阈值`；允许二星＝三星（产出粒度 0.5，紧关卡放不下三档）。**多产出关卡的星级阈值是各产出的合计**（单一标量），与目标值比较时用目标向量的合计
18. **对照关必须成对**：`关卡类别=对照` 的关卡，必须存在另一关与它**逐格同地形**（地形/地貌/资源/自然奇观/河流边全同）且**文明不同**。对照关要证明的是「换文明会换解法」，地形只差一格，差异就可能来自地形而不是文明（见 [../设计/关卡设计.md](../设计/关卡设计.md) §1.2）
19. **目标值与贪心基线的形态必须一致**：`目标类型=多产出同时达标` 时两者都写成 `产出类型:值` 用 `|` 分隔的向量，否则都写成标量。**规则 14 对多产出关卡逐项比较，不比合计** —— 贪心可能把预算全倒进一种产出，合计超过目标合计却有一项没达标，比合计会把合格关卡误判成不合格（见 [../设计/关卡设计.md](../设计/关卡设计.md) §7.4）

校验失败一律非零退出，不做警告了事。

### 怎么跑

```bash
python3 Tools/check_config.py             # 开发模式：缺表只警告
python3 Tools/check_config.py --delivery  # 交付模式：缺表 / 待核=是 / 未决母题 一律算错误
python3 Tools/check_config.py --schema    # 打印各表期望列（写 parse_civ6_xml.py 时对照用）
python3 Tools/check_config.py --dir <目录> # 改从别处读表（校验候选表 / 指向测试数据）
python3 Tools/test_check_config.py        # 回归测试：逐条断言每条规则真的会报错
```

只用标准库，系统 `python3` 即可，不需要建 venv。

两条设计取舍值得说明：

1. **缺表时跳过指向它的外键检查。** 否则一张表还没生成，所有引用它的行都会报错，把真正的问题淹掉。缺表本身已经单独报过一次。
2. **脚本里的 `SCHEMA` / `ENUMS` 是本文件的代码镜像。** 本文件才是唯一事实来源，改了字段或枚举必须同步改脚本——脚本头部的注释写了这条。

⚠️ **改了任何校验规则，去 `Tools/test_check_config.py` 补一条断言**。测试数据与说明见 [../Tools/testdata/README.md](../Tools/testdata/README.md)。

> 校验 5 对 `adjacency_rules` 的负值给警告（罕见但合法）；`combat_modifiers` 的负值是常态（沼泽、受损、渡海登陆），**连警告都不给**。两张表虽结构同构，负值的语义完全不同。
