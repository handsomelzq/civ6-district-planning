## 1. 设计目的

### 1.1 求值器就是这个项目

本作不做回合推进、不做 AI、不做战争。剥掉这些之后剩下的唯一系统就是：**给定一个局面，精确算出它产出多少、每个单位有多强，并说明每一点数值的来源。**

求值器输出**两棵树**：产出明细树与战斗力明细树。两者是同一种计算形态——基础值加上一串带来源的修正项（见 [../拆解/文明6-单位与军事叠力.md](../拆解/文明6-单位与军事叠力.md) §8），因此共用同一套累加机制与同一套拆解面板结构，**不是两个系统**。

三个消费方共用这一个函数：

| 消费方 | 用法 |
|---|---|
| 自由模式的拆解面板 | 对当前局面求值，渲染明细树 |
| 悬停预览 | 对「假设放置后的局面」求值，与当前值求差 |
| 挑战模式的目标判定 | 对当前局面求值，读取目标产出项 |
| （将来）批量求解器 | 对大量候选局面求值 |

**四个消费方、一个实现。** 任何一处规则逻辑漏到消费方里，这套复用就破了——武侠 demo 的战斗 SDD 已经踩过「结算耦合进动作」的坑，那边的代价是悬停预览要重写，这边的代价是四个功能各写一套规则。

### 1.2 设计目标：可追溯性优先于简洁性

求值器的输出不是一个数字，是**一棵树**，每个叶子携带贡献它的规则 id。

这不是为了好看。它换来三件事：

1. **数值错误可定位**：对账对不上时，能直接指到出错的表行，而不是在几百条规则里猜
2. **玩家能学会规则**：面板本身就是教学，不需要额外写说明
3. **拆解案与实现互为校验**：文档里写的规则与树里出现的规则 id 必须一一对应，任一边缺失都暴露问题

代价是实现更啰嗦——每一步都要记账。**接受这个代价。**

### 1.3 设计母题

本作的玩家体验母题是**「算清楚」**，不是「赌对了」。见 [GDD总纲.md](GDD总纲.md) §4：完全信息、无随机、无隐藏。

## 2. 玩家侧流程

求值器本身对玩家不可见，玩家通过三个表现接触它：

```
【悬停某个空格】
   ↓ 构造假设局面（当前局面 + 该格放入待选区域）
   ↓ 求值
   ↓ 与当前局面求值结果求差
   └─► 浮层：「放这里：科技 +A，生产力 +B」以及贡献这些增量的规则

【放置】
   ↓ 修改局面
   ↓ 重新求值
   └─► 拆解面板整树刷新；目标进度条刷新（挑战模式）

【展开拆解面板任一节点】
   └─► 逐层下钻至规则行：区域 → 产出类型 → 单条规则 → 规则 id
```

⭐ **悬停预览与真实放置走的是同一个函数**，区别只在于假设局面是否被写回。这保证了「预览说 +3，放下去真的 +3」——预览与结果不一致是这类游戏最严重的信任破坏。

## 3. 规则定义

### 3.1 输入：局面（boardState）

| 字段 | 内容 | 为什么必须有 |
|---|---|---|
| 地块集合 | 每格的坐标、地形、地貌、资源、自然奇观、河流边、其上的区域与建筑、**其上的单位** | 相邻判定与战斗修正的基础 |
| 单位状态 | 每个单位的 id、所属方、生命值、驻守回合数、编组等级、晋升 | 战斗修正的条件来源 |
| 大人物 | 位置与时代 | 大将军的加成需要**位置 + 时代匹配** |
| 城市集合 | 每座城的中心位置、人口、已建区域与建筑 | 合法性校验（工作范围、区域数上限） |
| 文明 / 领袖 | 标识 | 决定替换关系与产出修正 |
| **已解锁科技集合** | 科技 id 列表 | **见下方 §3.2，相邻规则带前置** |
| **已解锁市政集合** | 市政 id 列表 | 同上 |

### 3.2 为什么局面必须显式声明科技与市政 ⭐

文明 6 的相邻规则**带前置条件**：部分相邻加成要解锁特定科技或市政后才生效，另有部分会随科技推进而废弃。

这对一个**静态**求值器有一个必然推论：**只给地图和区域布局，产出是不唯一的。** 同一套布局在不同科技阶段产出不同。

因此：

- 局面必须显式携带已解锁科技与市政的集合，它们是求值输入，不是环境变量
- 残局关卡的定义里必须包含这两个集合（见 [SDD-挑战模式.md](SDD-挑战模式.md)）
- 自由模式需要给玩家一个「科技阶段」的选择或全解锁开关（待决策 D5）

**这是本项目最容易被漏掉的一条规则依赖。** 漏掉它的表现是：拆解面板的数字与游戏内对不上，且找不到原因——因为缺失的不是某条规则，而是规则的生效条件。

### 3.3 相邻加成的分档语义

文明 6 的相邻规则用一个「所需数量」字段区分两档：

| 档位 | 所需数量 | 语义 |
|---|---|---|
| 主要相邻 | 1 | 每个符合条件的相邻目标给满额加成 |
| 标准相邻 | 2 | 每 2 个符合条件的相邻目标给满额加成 |

单条规则的增量通式：

```
增量 = g( 相邻符合数, 所需数量, 加成值 )
```

`g` 的精确形态（整除截断 / 保留小数后统一取整 / 其他）**是 🔴 D4**，必须以游戏数据与游戏内实测确认，不得凭印象假定。它直接决定「3 个相邻区域在标准档下给多少」这类高频情形的结果，错一次会污染全部拆解。

### 3.4 相邻目标的类别

规则通过「目标类别 + 目标 id」指定它匹配什么。预期类别集合（**完整枚举待数据确认**）：

地形、地貌、资源、海洋资源、河流、区域、自然奇观、改良设施、自身同类区域。

匹配在**被求值区域的 6 个直接邻格**上进行。

### 3.5 求值顺序

顺序固定，不得调整——各步之间存在依赖。

```
1. 替换解析   应用文明/领袖的特色区域替换，得到「有效区域集」
2. 合法性校验 工作范围、区域数上限、建筑前置；非法项标记而不静默丢弃
3. 地块基础   每格的地形/地貌/资源/自然奇观基础产出
4. 区域基础   每个有效区域的基础产出
5. 相邻求值   对每个区域 × 每条适用规则，逐条计算并记账
6. 建筑增量   每个建筑的产出
7. 文明修正   领袖与文明的产出修正
8. 汇总取整   按产出类型聚合
```

**第 1 步在第 5 步之前**：替换必须先发生，否则会用被替换区域的规则去求值特色区域。

**第 8 步的取整时机是 🔴 D4 的一部分**：逐规则取整、逐区域取整、逐产出类型汇总后取整，三者结果不同。必须写死一种并与游戏对账。

### 3.6 单条相邻规则的求值步骤

```
对 区域R 的每一条适用规则 Rule：
  1. 前置校验：Rule.前置科技 ∈ 已解锁？否则跳过
  2. 废弃校验：Rule.废弃科技 ∈ 已解锁？则跳过
  3. 计数：R 的 6 个邻格中，满足 (Rule.目标类别, Rule.目标id) 的格数
  4. 增量 = g(计数, Rule.所需数量, Rule.加成值)
  5. 记账：向明细树追加叶子 { 增量, 计数, Rule.id, 产出类型 }
```

⭐ **第 5 步即使增量为 0 也要记账**（见边界 E1）：「为什么没有加成」与「有多少加成」是同等重要的信息。

### 3.7 输出：产出明细树

```
根
└─ 产出类型（科技 / 生产力 / 金币 / 信仰 / 文化 / 粮食 …）
   └─ 来源实体（某个区域 / 某个地块 / 城市中心）
      └─ 叶子 { 增量, 规则id, 计数, 档位 }
```

战斗力明细树结构平行：

```
根
└─ 单位（某个军事单位）
   └─ 修正通道（战斗力 / 远程 / 攻城）
      └─ 叶子 { 增量, 修正id, 命中次数 }
```

**硬约束（两棵树同样适用）**：任一节点的值 = 其所有子节点之和。不允许存在「其他」「杂项」节点。任何无法归因的数值都是建模缺失，必须补规则而不是塞进常数。

### 3.9 军事叠力的求值

#### 两种战斗力，必须分清 ⭐

文明 6 的部分修正只在攻击时生效、部分只在防御时生效，还有一类依赖对手的兵种（见拆解 §5.5）。因此「这个单位的最终战斗力」**不是一个数**：

| 值 | 组成 | 是否需要对手 |
|---|---|---|
| **驻守战斗力** | 基础 + `始终` + `防御时` 的全部修正 | 否 |
| **对抗战斗力** | 基础 + `始终` + `攻击时` + 兵种对抗修正 | 是，需指定对手兵种 |

**本作的「军事叠力」默认指驻守战斗力。** 理由：目标形态是"把一个单位堆到最强"，这是一个不依赖假想敌的、自足的优化问题；引入对手会让目标值依赖一个并不存在于局面中的对象，关卡也就失去了确定性。

对抗战斗力作为可选扩展：给定对手兵种时额外求一棵树。不进首期。

#### 单个单位的求值步骤

```
对 单位U：
  1. 取基础战斗力（按修正通道：战斗力 / 远程 / 攻城）
  2. 遍历 combat_modifiers 的每一条规则 M：
     a. 作用时机校验：M.作用时机 ∈ {始终, 防御时}（驻守战斗力）
     b. 条件判定：按 M.条件类别 检查 U 及其所在地块、邻格、大人物、状态
     c. 命中次数 n（侧翼/支援等按邻居计数，其余为 0 或 1）
     d. 若 M.是否可叠加 = 否，则 n 截断为 1
        若 M.叠加上限 非空，则 n 截断为上限
     e. 增量 = n × M.修正值
     f. 记账：向战斗力明细树追加叶子 { 增量, 命中次数, M.修正id }
  3. 汇总
```

⭐ 第 2c 步的「按邻居计数」与相邻加成的 §3.6 第 3 步是**同一个操作**。侧翼与支援本质就是军事层的相邻加成——实现上应复用同一个邻居计数函数，而不是各写一份。

#### 与产出求值的差异

| 维度 | 相邻加成 | 战斗修正 |
|---|---|---|
| 修正值符号 | 恒正 | **允许负值**（沼泽、受损、渡海登陆） |
| 分档机制 | 有（所需数量 1 / 2） | 无，改为「是否可叠加 + 叠加上限」 |
| 条件复杂度 | 只看邻格 | 看地块、状态、邻格、大人物、对手 |

这三处差异决定了两张规则表不能合并成一张，但求值机制可以共用。

### 3.8 不变量

| # | 不变量 | 为什么重要 |
|---|---|---|
| I1 | **纯函数**：不修改输入局面，不读全局状态，无随机，无时间依赖 | 四个消费方复用的前提 |
| I2 | **幂等**：同一局面反复求值结果恒等 | |
| I3 | **顺序无关**：产出是局面的函数，与区域的**放置历史无关** | 打乱放置顺序后总产出必须恒等。这是可自动测试的，见 §8 |
| I4 | **加和完备**：树的每一层求和等于父节点 | 拆解可追溯的前提 |

I3 值得单独强调：它意味着求值器**不能**有任何「按放置先后累加」的内部状态。这也是本作能做残局的根本原因——残局只给最终局面，不给历史。

## 4. 数据结构

| 表 | 本系统用到的内容 |
|---|---|
| `terrains` / `features` / `resources` / `wonders` | 地块基础产出；作为相邻目标时的匹配标识 |
| `districts` | 区域基础产出、成本、前置、是否特色区域、被替换区域 |
| `buildings` | 建筑产出、所属区域、前置 |
| `adjacency_rules` | **区域id, 目标类别, 目标id, 产出类型, 加成值, 所需数量, 前置科技, 废弃科技, 规则id** |
| `civs` / `leaders` / `unique_districts` | 替换关系、产出修正 |
| `units` | 基础战斗力（三通道）、兵种类别、**时代**（大将军匹配用）、战略资源需求 |
| `combat_modifiers` | **修正id, 条件类别, 条件参数, 修正通道, 修正值, 作用时机, 是否可叠加, 叠加上限** |

约定（与 `武侠RPGdemo` 保持一致）：多值字段用 `|` 分隔；键值对写作 `键:值`；空值写 `无`。

`adjacency_rules` 的 `规则id` 必须**稳定且唯一**——它会出现在玩家可见的拆解面板里，也是对账的锚点。由解析脚本生成时即固定，不随行序变化。

## 5. 状态机与流程

本系统**无状态机**（纯函数无状态）。有状态的是放置动作，属模式层。此处只给放置的合法性校验流程：

```
        ┌──────────────────┐
        │ 玩家选中待放区域   │
        └────────┬─────────┘
                 ▼
        ┌──────────────────┐   否   ┌──────────────┐
        │ 该格是否空闲？     ├──────►│ 不可放置，置灰 │
        └────────┬─────────┘        └──────────────┘
                 │ 是
                 ▼
        ┌──────────────────┐   否
        │ 在工作范围内？     ├──────► 同上
        └────────┬─────────┘
                 │ 是
                 ▼
        ┌──────────────────┐   否
        │ 地形是否允许？     ├──────► 同上
        └────────┬─────────┘
                 │ 是
                 ▼
        ┌──────────────────┐   否
        │ 区域数未超上限？   ├──────► 同上
        └────────┬─────────┘
                 │ 是
                 ▼
        ┌──────────────────┐   否
        │ 前置是否满足？     ├──────► 同上
        └────────┬─────────┘
                 │ 是
                 ▼
            可放置 → 求值预览
```

**不可放置一律置灰并给出原因**，不做「可点但报错」。这一条与武侠 demo 的内力不足处理保持一致。

## 6. 边界情况

按维度穷举。标「待定」的需在实现前确认。

### 数值与取整

| # | 情况 | 处理 |
|---|---|---|
| E1 | 相邻计数为 0 | **仍记账为 +0 并在面板中灰显**。理由：「这条规则存在但没吃到」是玩家最需要的信息 |
| E2 | 计数不能被所需数量整除（标准档 3 个目标） | **待定 → 🔴 D4**，以数据与实测确认 |
| E3 | 取整时机（逐规则 / 逐区域 / 汇总后） | **待定 → 🔴 D4**，三者结果不同，必须写死一种 |
| E4 | 产出为负 | 文明 6 的相邻加成无负值（本作不做负向相邻，见立项书 §三）。若数据中出现负值行，**解析脚本应报警**而不是静默接受 |

### 集合与匹配

| # | 情况 | 处理 |
|---|---|---|
| E5 | 一个邻格同时满足多条规则（既是山脉又在河边） | **各规则独立计数，互不排斥**。同一格可被多条规则各计一次 |
| E6 | 一个邻格上有区域，同时它的地形也匹配另一条规则 | **两条规则各自计数**。这不是双计错误——它们是不同的规则 |
| E7 | 被求值区域的邻格中有同类区域 | 按「自身同类区域」类别的规则处理，**以数据为准**，不假定有或没有 |
| E8 | 邻格在地图边界外 | 不计入任何计数 |
| E9 | 相邻目标 id 在对应表中不存在 | 跨表校验应拦截；运行时遇到则**报错而非跳过**，静默跳过会造成静默的数值错误 |

### 替换与继承（本系统最需要小心的一组）

| # | 情况 | 处理 |
|---|---|---|
| E10 | 特色区域是否继承被替换区域的相邻规则 | **待定 → 必须以数据为准**。文明 6 的特色区域在数据中有独立的规则行，因此**默认不假定继承**；实现按数据行走，并在拆解案中写明实际情况 |
| E11 | 其他规则中「相邻工业区」是否匹配汉萨 | **待定 → 🔴 D2**。这是最尖锐的一条：若不匹配，德国的布局逻辑会与常规文明产生结构性差异；若匹配，则需要一套「替换等价」的匹配规则。必须以数据确认，不可想当然 |
| E12 | 一个文明有多个特色区域替换 | 替换在 §3.5 第 1 步统一解析，互不干扰 |
| E13 | 替换后原区域是否仍可建造 | 以数据为准（文明 6 通常不可） |

### 前置与合法性

| # | 情况 | 处理 |
|---|---|---|
| E14 | 相邻规则的前置科技未解锁 | 规则跳过，但**仍在面板中灰显并标注「需要 X」**。这让玩家看见"再解锁一个科技这里会变好" |
| E15 | 建筑所属区域不存在 | 建筑不可建造，置灰 |
| E16 | 区域超出城市工作范围 | 不可放置 |
| E17 | 区域数超过人口上限 | 不可放置；上限公式引用配置表，见 🔴 D6 |
| E18 | 残局给定的局面本身违反合法性（关卡配错） | **加载时校验并报错**，不允许带着非法局面进入游戏 |

### 战斗修正（军事叠力）

| # | 情况 | 处理 |
|---|---|---|
| E21 | 修正值为负使最终战斗力 ≤ 0 | **下限截断为 1**，不出现 0 或负战斗力。同时在树中保留原始负值叶子，截断作为独立一项显示 |
| E22 | 同类修正命中多次但 `是否可叠加=否` | 计 1 次 |
| E23 | 命中次数超过 `叠加上限` | 截断到上限，**并在面板中标注"已达上限"**——玩家需要知道再加单位没用了 |
| E24 | 大将军在范围内但时代不匹配 | 不生效，但**灰显并标注"时代不匹配"**（与相邻规则前置未满足的处理一致，见 E14） |
| E25 | 多个大将军同时在范围内 | **待定 → 以一手数据确认是否叠加**。倾向不叠加（取最大），但这是猜测，不可写进实现 |
| E26 | 单位不在任何地块上（局面配错） | 加载时校验拦截 |
| E27 | 非军事单位（工人、商人等） | 不计算战斗力，不出现在战斗力树中 |
| E28 | 受损惩罚与生命值的映射 | 见拆解 §10，二手资料存在冲突，**一手核对前不得实现** |
| E29 | 单位所在地块同时满足多条地形地貌修正（林+丘） | **各自独立计数并叠加**，与相邻规则的 E5 同理 |

### 顺序与历史

| # | 情况 | 处理 |
|---|---|---|
| E19 | 不同放置顺序得到同一最终局面 | **产出必须完全相同**（不变量 I3）。有自动测试，见 §8 |
| E20 | 撤销放置 | 局面回退后重新求值；求值器无历史状态，故无需反向计算 |

## 7. 与其他系统的接口

### 输入

| 来源 | 数据 |
|---|---|
| 配置表层 | 全量规则与数值。**求值器不硬编码任何规则** |
| 模式层 | 局面（boardState），含科技与市政集合 |

### 输出

| 目标 | 数据 |
|---|---|
| 自由模式 | 产出明细树（渲染拆解面板） |
| 挑战模式 | 产出明细树（读取目标产出项做判定） |
| 悬停预览 | 两次求值结果的差 |

### 架构约束

```
        模式层 / UI          ← 依赖引擎或框架
            ↕  只传局面，只收明细树
        求值器（纯函数）      ← 零引擎依赖，零框架依赖
            ↕
        配置表层
```

- 求值器**不得依赖任何引擎或 UI 框架**（对齐 [工程规范 §3.2](../../游戏制作学习/04-独立Demo制作流程与工程规范.md)）
- 求值器**不得持有可变状态**
- 模式层**不得实现任何产出规则**

这三条各自对应一个能力：第一条使求值器能脱离界面跑批量对账与将来的求解器；第二条保证四个消费方复用安全；第三条保证规则只有一处实现。

## 8. 验收标准

### 纯度与不变量

- [ ] 对同一局面连续求值 N 次，结果完全相同（I2）
- [ ] 求值前后对局面做深比较，无任何字段被修改（I1）
- [ ] **顺序无关测试**：取一个目标局面，用随机打乱的放置顺序构造 N 次，每次的总产出与明细树完全一致（I3）
- [ ] **加和完备测试**：遍历明细树，每个非叶节点的值等于其子节点之和，且不存在「其他」节点（I4）

### 数值对账（最关键）

- [ ] 从游戏内截取 ≥10 个已知局面，逐项核对产出与拆解，**通过率 100%**
- [ ] 对账用例覆盖：主要档相邻、标准档相邻、标准档的非整除情形、带前置科技的规则、特色区域（德国汉萨）、多规则同时命中同一邻格
- [ ] 对账失败时定位到具体规则 id，修正解析或规则理解，**不允许通过调整数值使其对上**

### 军事叠力

- [ ] 驻守战斗力的拆解可追溯到每条 `修正id`
- [ ] 地形地貌修正叠加正确（以「森林覆盖的丘陵」验证 E29）
- [ ] 叠加上限生效且面板标注「已达上限」（E23）
- [ ] 大将军的**时代匹配**判定正确，不匹配时灰显标注（E24）
- [ ] 侧翼/支援的邻居计数与相邻加成**调用同一个计数函数**（代码层检查，非行为检查）
- [ ] 负值修正正确，且最终战斗力不低于 1（E21）
- [ ] 非军事单位不进入战斗力树（E27）

### 规则完整性

- [ ] 拆解案中记载的每条规则，都能在 `adjacency_rules` 中找到对应行
- [ ] 反向：表中每条规则都能被至少一个测试局面触发（未被触发的规则要么是数据噪音，要么是测试覆盖不足，两者都要查清）
- [ ] E1 情形下规则灰显，E14 情形下标注前置

### 合法性校验

- [ ] E15–E18 各情形均不可放置且给出原因
- [ ] 关卡加载时对非法局面报错

## 10. 🔴 待决策清单

### 阻塞实现

**✅ D1 · 「军事叠力」的精确定义 —— 已解除（2026-09-23）**
定义为：**单个军事单位在全部加成叠满后呈现出的最终战斗力**。
实现上取「驻守战斗力」（基础 + `始终` + `防御时` 的修正），不依赖假想敌；对抗战斗力作为可选扩展不进首期。见 §3.9 与 [../拆解/文明6-单位与军事叠力.md](../拆解/文明6-单位与军事叠力.md)。

**🔴 D8 · 多个大将军是否叠加**（= 边界 E25）
二手资料未覆盖，必须一手确认。这条影响残局关卡的设计空间（能否用堆大将军的方式冲高战斗力）。

**🔴 D9 · 受损惩罚的精确曲线**（= 边界 E28）
二手资料自相矛盾（"每 10% 减 1、上限 −10" vs "最多减半"）。一手核对前不得实现。

**🔴 D2 · 替换等价的匹配规则**（= 边界 E11）
其他规则中的「相邻工业区」是否匹配汉萨？以数据确认后写死。

**🔴 D3 · 相邻计数的目标去重**
同一邻格被同一条规则的多个匹配维度命中时是否只计一次。以数据结构确认。

**🔴 D4 · `g` 的形态与取整时机**（= 边界 E2、E3）
标准档非整除怎么算、取整发生在哪一层。**必须以游戏数据 + 游戏内实测双重确认**，这是全文档最高优先级的未定项：它影响每一条标准档规则的每一次求值。

### 可在结构层之后决定

- D5 · 自由模式的科技阶段如何呈现（阶段选择器 / 全解锁开关 / 自定义勾选）
- D6 · 区域数上限的公式来源（引用配置表字段，公式以数据为准）
- D7 · 是否纳入工人与改良设施（改良设施与区域是两套相邻体系，纳入会显著扩大范围）
