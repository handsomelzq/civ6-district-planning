# 文明 6 区域规划 · 立项书

> 立项：2026-09-23（取代 09-20 早先的「六边形区域放置小游戏」立项，方向已由**简化复刻**改为**高保真还原**）
> 参考来源：《席德·梅尔的文明 VI》（Steam 时长 339.1 h）
> 对应作品集：#2 文明 VI 系统拆解、#4 原创系统策划案、#5 可玩原型 —— **一个项目同时打三个作品位**
> 目标岗位：**系统策划 + 数值策划**

---

## 一、一句话

一个**高保真还原文明 6 产出规则**的区域规划工具与残局关卡集：玩家在给定局面上排布区域、建筑与单位，实时看到每一点产出由哪几条规则贡献，并以此挑战指定目标。

## 二、为什么做这个

文明 6 的区域相邻加成是一套**完全数据驱动**的系统：所有规则以数据行的形式存放在游戏数据库里（相邻规则位于 `Districts.xml` 的 `Adjacency_YieldChanges` 与 `District_Adjacencies`），启动时灌入 SQLite。这意味着：

1. 它可以被**精确还原**，而不是凭手感模仿——这是本项目的立身之本
2. 还原过程本身就是最硬的系统拆解：从一手数据反向工程出规则体系，比任何二手资料的复述都可信
3. 它与国土空间规划的专业背景天然咬合，但**本项目不改题材**——完全对标文明 6，保持拆解与实现的严格同构

**这个项目的卖点不是"我做了一个像文明 6 的游戏"，而是"我把文明 6 的产出规则精确还原到可对账的程度，并在其上做了关卡设计"。** 前者是模仿，后者是系统与数值能力的证明。

## 三、两个模式

### 自由模式（沙盒）

选定文明与领袖，在地图上自由排布区域、建筑与单位，追求理想布局。

核心体验不是"赢"，而是**看懂**：产出拆解面板把每一点产出摊开到规则级别——这座学院的科技产出，是「区域基础产出」加「相邻 2 座山脉（主要档）」加「相邻 3 个区域（标准档）」加「图书馆」四项构成的，每一项都标着它来自哪条规则。

### 挑战模式（残局闯关）

给定一个已有局面与一个目标（例：生产力达到 N / 科技达到 N / 军事叠力达到 N），玩家在约束下完成排布。

"残局"是关键设计选择：它使本项目**不需要模拟完整的文明 6**，只需要精确求值 + 有限步编排。

### 第三模式（暂缓）

原创机制（如负向相邻／负外部性）不进前两个模式。文明 6 本体没有负向相邻，混进去会破坏"严格对标"这一前提。若要做，作为独立的第三模式，与还原部分隔离。

## 四、范围

### 做

| 项 | 说明 |
|---|---|
| 地块基础产出 | 地形 / 地貌 / 资源 / 自然奇观 |
| 区域 | **全部区域**，含各类特色区域 |
| 建筑 | **全部建筑**及其产出与前置 |
| 相邻加成 | 完整的相邻规则体系，含主要／标准两档语义 |
| 文明与领袖 | **3–5 个**，含德国（汉萨替代工业区） |
| 单位 | 仅军事叠力目标所需部分 |
| 产出拆解 | 每一点产出可追溯到贡献它的规则行 |

### 不做

回合推进、生产／科技／市政队列、AI 对手、战争结算、外交、宗教传播、地图生成、迷雾、单位移动与寻路、城市增长与人口分配（仅作为求值输入的既定状态）。

**本项目是「静态局面求值器 + 残局」，不是 4X 模拟器。** 这一条界定了九成的工作量归属，任何"要不要加一点点回合"的念头写进暂缓清单，不进版本。

暂缓清单：
- 负向相邻／原创机制（→ 第三模式）
- 求解器与参考最优解评级
- 地图程序生成

## 五、数据来源与版本声明

**所有数值来自游戏本体数据文件，不采信二手资料。**

| 项 | 内容 |
|---|---|
| 提取路径 | 本机 Steam 安装目录下的游戏数据 XML（含各资料片的覆盖数据） |
| 提取方式 | `Tools/parse_civ6_xml.py`，脚本入库 |
| 可复现性 | 删除全部配置表后重跑脚本可完全重建 |
| 版本标注 | 游戏版本号与提取日期写入本文件与各拆解文档首页 |
| 资料片依赖 | **政府广场属《迭起兴衰》**；堤坝／运河／地热裂缝相邻属《风云变幻》。缺对应资料片则该规则在数据中不存在，范围随之调整 |

> 版本号与提取日期：待游戏安装完成后填写（❓）

### 过渡期政策（游戏安装前）

游戏未安装期间允许用二手资料先搭模型，但必须满足三条：

1. 每张生成表带 `数据来源` 与 `待核` 两列（见 [../配置表/字段说明.md](../配置表/字段说明.md) §零）
2. 二手来源在对应拆解文档中逐一列明
3. **`待核=是` 的数据不得出现在任何对外产物中**（演示视频、作品集 PDF、README）。交付前跑检查，存在未核项即阻断交付

目的：二手资料可以用来验证架构是否成立，但不能用来对外声称精度。**这条边界是这份作品可信度的底线。**

**为什么这一节重要**：一份以数值精度为卖点的作品集，数值错误等于可信度归零。声明数据来源与版本，是把"我核对过"变成"可验证"。

## 六、配置表设计（核心卖点）

| 文件 | 内容 |
|---|---|
| `terrains` / `features` / `resources` / `wonders` | 地块侧的产出与相邻资格 |
| `districts` / `buildings` | 区域与建筑的基础产出、成本、前置 |
| `units` | 军事单位与战斗力构成 |
| `civs` / `leaders` / `unique_districts` | 文明领袖修正与特色区域替换关系 |
| `adjacency_rules.csv` | **相邻规则表，一行一条规则** |
| `levels.csv` | 残局关卡定义 |

`adjacency_rules.csv` 独立成表而非塞进 `districts`，与文明 6 原本的表结构同构。但本项目采用 **`目标类别 + 目标id` 两列的多态写法**，而文明 6 原表用一组可空列（相邻地形／相邻区域／相邻资源…各占一列，每行只填一个）表示目标类型。

**这个差异值得在面试时主动讲**：原表是宽稀疏表，新增目标类型要加列；多态写法新增类型不动表结构。这说明理解的不只是"规则是什么"，还有"规则为什么这样存"以及"能不能存得更好"。

## 七、完成标准

不设时间节点。按能力达成判定，逐条勾。

### 数值层

- [ ] 全部区域、建筑、相邻规则从游戏数据完整解析入表
- [ ] **数值对账通过**：解析结果与游戏内已知局面逐条核对一致（对账用例须覆盖主要档、标准档、标准档的非整除情形、带前置科技的规则、特色区域）
- [ ] 删除全部配置表后重跑解析脚本能完全重建
- [ ] 跨表引用校验全部通过

### 系统层

- [ ] 求值器是纯函数：同一局面反复求值结果恒等，且不修改局面
- [ ] 产出拆解可追溯到规则行级别
- [ ] 特色区域对原区域规则的继承与覆盖行为正确（以德国汉萨验证）

### 体验层

- [ ] 自由模式：能选文明领袖、自由排布、实时看到产出拆解
- [ ] 挑战模式：能加载残局、判定目标达成、给出评分
- [ ] 录出演示视频，重点演示"改一行相邻规则，最优布局随之改变"

### 文档层

- [ ] 拆解案四篇完成，数值全部有出处
- [ ] 各 SDD 的边界情况与验收标准两节非空

## 八、与其他 demo 的关系

`武侠RPGdemo` 是独立项目，两者不合并。早先「把区域规划内核并入武侠 demo 作为阵法子系统」的方案随本次方向变更作废——本项目已从"一个相邻加成小游戏"变成"文明 6 规则的精确还原"，内核不再是可移植的通用模块。
